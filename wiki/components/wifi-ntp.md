# WiFi & NTP

Connectivity on Watchy is deliberately on-demand: radios are off during deep sleep and only activated for specific operations — NTP sync and weather fetching. This component is the counterpart to the [RTC](../components/rtc.md) that keeps time when offline, and it feeds the [Power Budget Analysis](../syntheses/power-budget.md). *Verified against the repo at `d1d233c` as of 2026-08.*

**Provisioning.** `setupWifi()` (`Watchy.cpp:911`) uses the WiFiManager library to capture credentials. It calls `wifiManager.resetSettings()`, sets a 60 s timeout (`WIFI_AP_TIMEOUT`), registers `_configModeCallback` to draw the AP name/IP/MAC to the [Display](../components/display.md), then `autoConnect(WIFI_AP_SSID)` with SSID "Watchy AP". On success it resets `weatherIntervalCounter = -1` to force the next weather read and stashes the IP/SSID into the [RTC_DATA_ATTR](../concepts/rtc-data-attr.md) fields `lastIPAddress`/`lastSSID`. Setup runs with the display's lightsleep callback disabled, then restores it and turns the radios back off.

**Connection.** `connectWiFi()` (`Watchy.cpp:958`) calls `WiFi.begin()` (no credentials — WiFiManager persists them in NVS) and `WiFi.waitForConnectResult()`, returning and setting the `WIFI_CONFIGURED` flag. On failure it powers down radios with `WiFi.mode(WIFI_OFF); btStop()`.

**Weather.** `getWeatherData()` → `_getWeatherData()` (`Watchy.cpp:694`) is the fetch path behind display of weather on [watchfaces](../concepts/watchfaces.md). It is rate-limited by the [RTC_DATA_ATTR](../concepts/rtc-data-attr.md) `weatherIntervalCounter`: initialized to `-1` (force a fetch on first use), then it only performs a live fetch once `updateInterval` (default 30 min) has elapsed, otherwise it returns the cached `currentWeather` and simply increments the counter (`Watchy.cpp:749-752`). When a fetch *does* run it substitutes `{cityID}`/`{lat}`/`{lon}`/`{units}`/`{lang}`/`{apiKey}` placeholders into the configured `weatherURL`, fires an HTTP GET with a 3-second connect timeout, and on HTTP 200 parses the JSON into a `weatherData` struct (temperature, condition code, description, sunrise/sunset, and `external = true`). As a side effect, it derives the GMT offset from the API's `timezone` field and calls `syncNTP(gmtOffset)`.

**Offline fallback.** If `connectWiFi()` fails during that window, `_getWeatherData()` falls back to the **BMA423's on-chip temperature** ([BMA423 Accelerometer](../components/bma423-accelerometer.md)) for `currentWeather.temperature`, forces `weatherConditionCode = 800` (clear sky) and `external = false` (`Watchy.cpp:740`). Faces should use the `external` flag to distinguish a weather-API reading from this local estimate, which has no condition/description/sunset data.

**NTP.** `syncNTP()` (`Watchy.cpp:1131`, plus overloads) builds an `NTPClient` against `settings.ntpServer` with the given GMT offset, calls `forceUpdate()`, and on success writes the epoch time back into the RTC via `RTC.set(tm)`. The "Sync NTP" menu item wraps this: it connects WiFi, syncs, draws the resulting time, then powers radios back off. The RTC is the source of truth that survives the radios being off, so keeping it synced is what makes [watchfaces](../concepts/watchfaces.md) accurate.

All tunables — `cityID`, `lat`, `lon`, `weatherAPIKey`, `weatherURL`, `weatherUnit`, `weatherLang`, `weatherUpdateInterval`, `ntpServer`, `gmtOffset` — come from the `watchySettings` struct in [Board & Config](../components/board-config.md).
