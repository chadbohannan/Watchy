# Display (WatchyDisplay)

The e-paper panel is a 200×200 monochrome display, driver class `WatchyDisplay` deriving from `GxEPD2_EPD` in `src/Display.h`. It wraps the GxEPD2 library (by Jean-Marc Zingg) for SQFMI's panel — a Good Display GDEH0154D67 with an SSD1681 controller. The template header notes the original GxEPD2 example was modified to improve performance for Watchy. Because the vendored class must satisfy GxEPD2's evolving interface, a GxEPD2 upgrade once broke builds until v1.4.7 — see the [GxEPD2 1.5.2 compile break incident](../incidents/2023-04-18-gxepd2-width-visible.md). *Verified against the repo at `d1d233c` as of 2026-08.*

The core timing constants live in `Display.h`: `power_on_time` 100 ms, `power_off_time` 150 ms, `full_refresh_time` 2600 ms, and `partial_refresh_time` 500 ms. `reduceBoosterTime` is set true to save roughly 200 ms on the panel's booster ramp — a deliberate latency-vs-reliability tradeoff on a device that wakes from sleep to draw a clock. The booster-shortening is real in `_InitDisplay()` (`Display.cpp:426`): it writes the SSD1675B booster soft-start control register with all three phase drive strengths forced to maximum (`0xF4`) and a zero phase-duration byte, trading waveform margin for ~200 ms of lower power-on latency.

The driver talks to the panel over the ESP32's hardware SPI. The constructor (`Display.cpp:27`) was customized to start SPI with the V3 pins when building for `ARDUINO_ESP32S3_DEV` and to select a 20 MHz `SPISettings` (the base GxEPD2 base class otherwise assumes a different bus). `initWatchy()` (`Display.cpp:38`) drives the default full-power init, gated by the module-level `RTC_DATA_ATTR bool displayFullInit` flag, which is cleared only after the first full update (`_Update_Full`, `Display.cpp:485`) so the panel is initialized hard only on first boot rather than on every wake.

Two refresh paths matter to the [deep sleep & wake model](../concepts/deep-sleep-wake.md). Full refresh reinitializes the panel and is used on structural changes (reset, entering the menu, new screens). Partial refresh is fast and used on the per-minute clock tick in `showWatchFace()` and during menu navigation. `asyncPowerOn()` (`Display.h:42`) lets the panel power on in the background while the watchface is being drawn: `_PowerOnAsync()` (`Display.cpp:362`) sends the power-on command and sets `waitingPowerOn` without blocking on busy, so the CPU can draw while the panel's driver voltages ramp; the eventual update's own busy-wait then completes the sequence. This overlaps the panel's slow power-on with the CPU's drawing work.

The busy pin is wired to an interrupt-capable GPIO, and `WatchyDisplay::busyCallback` (`Display.cpp:21`) enables `ESP_LIGHT_SLEEP` while the panel is busy, parking the CPU during long operations. `setupWifi()` (`Watchy.cpp:911`) temporarily replaces this callback with a no-op because the WiFi provisioning flow must keep the CPU awake, then restores `busyCallback` afterward. The display also hand offs power saving: `deepSleep()` calls `display.hibernate()` before bedtime. `hibernate()` (`Display.cpp:330`) writes the SDD1681 deep-sleep command (`0x10`/`0x01`) to drop the controller's draw but deliberately skips `_PowerOff()` since the whole SoC is about to power down. Importantly, the same display object holds the `_hibernating` flag that `asyncPowerOn()` and `setDarkBorder()` check, so a hibernated display is reinitialized (`_reset()`, `Display.cpp:414`) before it is drawn again after waking.

The display is owned as a static singleton, `Watchy::display`, instantiated in `Watchy.cpp:10` as `GxEPD2_BW<WatchyDisplay, WatchyDisplay::HEIGHT>`. All rendering from [watchfaces](../concepts/watchfaces.md) targets this object, which is why faces draw directly to the panel through the [Watchy Firmware](../systems/watchy-firmware.md) rather than through a framebuffer abstraction. Image writes clamp coordinates and widths to byte boundaries (`_writeImage`, `Display.cpp:108`) and use the controller's `0x26` (previous frame) buffer for fast updates, enabling ghost-reduction differential updates (`writeImageForFullRefresh` writes both `0x26` and `0x24`).
